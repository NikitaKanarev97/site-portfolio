# Данные, визуальные артефакты и движение

03.10.2026. Решения для общего этапа следующей реализации. Этот документ не означает, что указанные расширения уже есть в runtime. Текущее состояние и будущий контракт различаются ниже явно.

## 1. Две дизайн-системы

**ДС портфолио** — сетка, типографика повествования, поверхности, отступы, доступность, хореография. Источники: `ds/tokens.css`, `ds/motion.js`, `ds/foundation.md`, `ds/components.md`, `ds/patterns.md`, `ds/motion-concept.md`. Зеркала в `src/` обновляются тем же изменением.

**ДС показываемого продукта** — его реальные шрифты, цвета, компоненты и состояния. Она живёт в соседнем продуктовом проекте. Её образец является материалом кейса: цвета Learn не заменяют акцент портфолио, а оболочка портфолио не перекрашивает интерфейс Learn.

Сохраняем текущий foundation. Небольшие дополнения к семантическим ролям допускаются на общем этапе после конкретного примера в двух кейсах. Замена Manrope, общей палитры или всех радиусов не включается в план автоматически.

## 2. Что уже работает и что требуется

| Область | Есть | Изменение следующего этапа |
|---|---|---|
| Контент | `src/copy/cases/*.ts` и `src/copy/ru/cases/*.ts` | Эти файлы остаются носителем опубликованного текста |
| Pilot | Отдельные copy и preview Agent Ops | Сохранить как контрольный образец до завершения штатного переноса |
| Новый CaseStory | Общие факты, cover, optional поля по десяти фиксированным ролям | Ввести упорядоченную композицию, не привязанную к одинаковым секциям |
| Опубликованный маршрут | EN `[slug].astro`; RU передаёт entry в него | Один renderer нового story; fallback прежней страницы пока история кейса не готова |
| Диаграммы | `Diagram`, schema, map/flow/prototype/library, четыре kit-образца | Добавить продуктовые данные только для отобранных схем |
| Библиотека продукта | SVG-library рисует восемь типов обычных контролов | Доменный UI показывать реальными specimens; не расширять имитацию до всего продукта |
| Medиа | Штатные product folders; Agent Ops pilot media | Для новой редакции отдельные папки, чтобы старые маршруты сохранялись до интеграции |

**Никакого CMS-этапа сейчас.** Пять кейсов уже имеют типизированные локальные данные. Directus, новая база, сервис аналитики и перенос в React не решают нынешнюю задачу. Контент, доказательства и медиа можно контролировать файлами.

## 3. Минимальный будущий контракт

Сохраняются `cover`, `facts`, `theme`, `prototype` и существующие типы отдельных модулей. Вводится `blocks: CaseBlock[]` — упорядоченный union поверх готовых модулей: thesis, numbers, artifact, comparison, process, steps, shot, detail, specimen, outcome. Названия union и точные сигнатуры фиксирует общий этап после проверки Agent Ops и фрагмента Portal; новая библиотека компонентов с нуля не нужна.

Каждый блок имеет стабильный `id`, тип и payload; доказательный материал связывается с `evidenceId` / `mediaId`. Режим движения — разрешённый смысловой variant, не произвольный GSAP-код в data. Несколько разных блоков могут использовать один и тот же модуль. Cover/facts находятся перед blocks; следующий кейс вычисляется снаружи story, после результата.

Не поддерживать два полноценных формата story бессрочно. Общий этап переносит pilot и демонстрационный фрагмент Portal, сохраняет явный legacy fallback для опубликованных старых entry; каждый готовый кейс получает новый story. После миграции всех пяти legacy ветка удаляется интегратором.

**Двуязычие.** Состав и стабильные id блоков совпадают, строки локализованы в существующих EN/RU-файлах. Факты, evidence и геометрия не дублируются ради перевода. RU-вёрстка проверяется самостоятельно: автоматический перевод не считается редакционной приёмкой. У Pawly текущая версия EN/RU; устаревшее правило «прототип Pawly только EN» не применять. Возможности локализации Vet проверяются по текущему accepted продукту, не по старому общему абзацу.

## 4. Реестр доказательств и Impact

Для каждого кейса создать `tasks/portfolio-rebuild/<slug>/evidence.md`; в нём одна строка на публикуемое утверждение.

| Поле | Содержание |
|---|---|
| ID | Стабильная ссылка из истории, например `portal-shipped` |
| Утверждение | Что именно показываем или сообщаем |
| Тип | факт владельца / измерение / оценка / QA / гипотеза / демо |
| Версия | исходный проект / нынешняя пересборка / текущий accepted прототип |
| Источник | Путь и раздел документа; для факта владельца — подтверждение в текущей карте |
| Граница | На ком, когда, сколько наблюдений, что не следует из результата |
| Публичная формулировка | Короткая EN/RU-пара, сохраняющая статус |

При расхождении источников не усреднять факты. Подтверждённые владельцем факты и текущая публичная карта имеют приоритет над старым synthetic briefing; конфликт записывается в evidence. Число из старой приёмки сохраняет её дату и охват.

**Outcome-блок** допускает качественный результат, число либо сравнение. В данных должно быть понятно, что является результатом, что доказательством и что компромиссом. Три числовые карточки не обязательны. Большой процент не ставится без измерения; компонентный inventory и число QA-проверок не заменяют продуктовую ценность.

Пример допустимой структуры, а не готовый код:

```text
result: «Прототип проверен, доработан и принят»
evidence: client-acceptance — подтверждение владельца, UX-проверка текущего прототипа
tradeoff: «Каждая выплата ждёт человека»
nextEvidence: «После внедрения измерить безопасное расширение автономии»
```

Неизвестное измерение остаётся вопросом в evidence. На публикуемом сайте `TODO(owner)` и неподтверждённые цифры не выводятся: допустимое качественное утверждение используется вместо них, либо блок не публикуется.

## 5. Диаграммы и рабочие артефакты

Хранилище продуктовых схем: `src/data/diagrams/<slug>/<name>.ts`. Нотация общая, содержание индивидуальное. Map показывает владение и масштаб, flow — переходы и решения, prototype-map — связь конкретных экранов. Все виды одновременно не обязательны.

**Визуальный контракт:** [artifact-visual-spec.md](artifact-visual-spec.md) с четырьмя исходными изображениями. Flow сохраняет старт-подпись с чертой, прямоугольник шага, ромб решения, параллелограмм ввода и ответы на связях; map — иерархию без стрелок и функциональные группы. Паспорт выбранного материала заполняется до отрисовки. На общем этапе A уточнить map-паттерн: синий номер внутри верхнего правого угла как у HA вместо текущего ink-маркера над плашкой; токен и mirror обновляются вместе. Это плановое изменение, не описание нынешнего runtime.

Каждая публичная схема имеет source, summary и подпись: исходный артефакт / перерисовка текущего проекта / редакционная схема для кейса. Полный roadmap не выдаётся за реализованное покрытие. Номера узлов при необходимости связываются с настоящими экранами, но число узлов не называется числом построенных страниц.

Mobile: смысловой фрагмент 5–8 узлов либо самостоятельная вертикальная компоновка; при сохранении полного графа горизонтальное чтение ограничено его контейнером. Текстовое summary остаётся доступным. Нельзя просто уменьшить огромную схему до нечитаемости. Отдельная mobile-геометрия требует поддержки общего контракта; сейчас единая EN/RU-геометрия автоматически её не создаёт. Общий этап выбирает и документирует поддержку mobile-варианта или читаемого фрагмента на примере Portal, без отдельного самодельного renderer у case-чата.

Для Audit → Direction достаточно сопоставления 2–3 наблюдений и выбранных правил. Для процесса достаточно одного отобранного рабочего материала с выводом. Новая схема или новый эскиз не выдаются за исторический скрин Miro/Figma. Генерируемый фон — редакционное оформление; не доказательство проведённого исследования.

## 6. Лист дизайн-системы

`kit/library.ts` остаётся условным образцом на `/kit`. Его палитра, семейство Inter и телеком-контент не переносятся в чужой продукт. Нынешний library-паттерн поддерживает общие контролы и без загрузки шрифта может использовать fallback; он не обеспечивает точность доменных компонентов.

**Выбранный способ:** actual specimens из accepted каталога или целого DOM-компонента исходного проекта + компактная типографика и палитра, взятые из актуальных product tokens. Композиция листа — через готовые CasePlate / CaseShot / CaseCarousel; если необходим новый specimen-variant, общий этап один раз описывает и добавляет его в ДС. `CaseArtifact` сейчас принимает только Diagram, поэтому raster/actual-specimen нельзя молча передать ему как готовый supported payload.

Главный лист Portal следует `HA-DS-01`: foundation слева примерно на треть ширины, доменные матрицы справа; четыре колонки типографики, палитра под ней, состояния вертикально в пунктирных группах. До capture отобрать 5–6 реальных типографических ролей, 8–12 нужных свотчей, 4–6 семейств и обычно 2–4 значимых состояния на семейство. Если существенных состояний больше, вынести семейство в детальный кадр, а не удалять состояние ради лимита. На 390 — три отдельных читаемых материала вместо миниатюры большого desktop-постера. Для Learn — тема в применении; для Pawly — 3 уже существующие матрицы. Точный состав и допустимые адаптации — в визуальной спецификации и `artifact-plan.md`. Импорт runtime продуктовых React-компонентов в Astro-портфолио ради статичного листа не нужен.

## 7. Реестр медиа

Создать `tasks/portfolio-rebuild/<slug>/media.md`: id, файл, продукт/версия, исходный маршрут или story, viewport/DPR, locale, fixture, авторство/право использования, назначение desktop/mobile, статус актуальности. Для каждого кадра указать, нужен ли новый capture или можно переиспользовать имеющийся.

Для артефактов добавить ссылку на паспорт в `artifact-plan.md`, ID выбранного эталона и конкретную область будущего листа. Состав и раскладка фиксируются до capture; переиспользуемый кадр также сверяется с эталоном. Паспорт — локальная рабочая спецификация, не дополнительный запрос разрешения владельцу.

Новые медиа: `public/media/rebuild/<slug>/`. Базовый материал не редактируется внутри изображения так, чтобы изменить факт или UI. Коллаж допускает композицию реальных кадров, но не дорисованные интерфейсы. Целые панели и внутренние поля сохраняются; focus-кроп обозначается деталью и не обрезает главное действие.

MP4/WebM + постер для клипов. Цель до 2 МБ на короткий клип; длинный понятный ролик не ускорять до нечитабельности ради бюджета. Сначала сократить сценарий и разрешение, затем отдельно обосновать исключение. У существующего Pawly return-proof сохраняется понятное воспроизведение с native controls.

Оригиналы и записи проверки остаются в локальном evidence-архиве, итоговые site media — в `public/`. Полные кадры конкурентов и их assets не становятся материалом опубликованного портфолио.

## 8. Движение: общий словарь, разные сцены

| Смысл | Режим / компонент | Применение | Статика / reduce |
|---|---|---|---|
| Вход в работу | CaseCover, lines / proof / screen | Короткий доступный тезис; UI читается сразу | Конечная композиция |
| Переход к рассказу | CaseSheet / sheet | Только если обложка помещается и наезд помогает | Обычный поток |
| Пояснить структуру | Diagram / draw | 1 раскрытие значимой связи | Все узлы и связи видны |
| Изменение решения | CaseSteps / pin-swap / focus | Одна центральная сцена; composition выбирается под продукт | Вертикальный список |
| Дополнительные материалы | CaseCarousel | Пользователь выбирает следующий материал | Первый основной слайд доступен |
| Показать взаимодействие | Настоящий клип | Одно завершённое действие | Постер + конечные состояния, явный play при необходимости |
| Продолжить просмотр | CaseNext / marquee / transition | Большая обычная ссылка | Статичное название и ссылка |

Конкретные параметры берутся из `ds/motion.js`, а не копируются из CSS конкурента в компонент. Новая хореография регистрируется через `withMotionPreference()` и описывается в motion-concept. Анимация состояния продукта не меняет демонстрационные данные ради красивого счётчика.

**Последняя настройка CaseNext:** без Pause title motion и pause на hover/focus; движение зависит от видимости и reduced motion. Настройка сохраняется при переносе. Клики и клавиатурная активация ведут по ссылке; колесо или End не переключают страницу.

Pin — opt-in при достаточной ширине и высоте. На 360/390, коротком окне, reduce и no-JS нужен дочитываемый native flow. Очерёдность сцен и конечные кадры понятны при обратном и быстром скролле. Видео и сцены освобождают ресурсы при уходе; Back возвращает место без повторного вступления.

## 9. Проверка системы перед параллельной работой

Общий этап демонстрирует текущий Agent Ops и **другой тип истории**: фрагмент Portal с настоящим specimen, IA и качественным Outcome. /kit проверяет reusable variants. Это показывает гибкость системы до четырёх одновременных реализаций.

Статичные состояния: 1440, 1024, 390, 360 и 1440×600; обе локали для новых общих ролей. Full/reduce/no-JS, реальный resize, переход и Back. `npm run check`, `build`, `check:css`, параметризованный `check:harmony` после чтения текущего скрипта; побайтовые зеркала tokens/motion. Нужные расширения harmony снимают обязательный минимум слов и фиксированный состав секций, сохраняя читаемость и ритм.

CPU-замер проводится отдельно от capture/encoding и других браузерных прогонов. Сравниваем повторяемые локальные прогоны в одинаковых условиях. LCP/CLS локального preview не объявляются полевыми CWV. Художественная приёмка включает кадры и запись движения: автоматический PASS не означает «выглядит хорошо».
