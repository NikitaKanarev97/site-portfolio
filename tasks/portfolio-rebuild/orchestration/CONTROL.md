## Действия при каждом пробуждении

1. Прочитай STATE.json, этот файл и актуальный handoff. Не запускай существующий этап заново из-за того, что повторно сработал heartbeat.
2. Используй wait_threads с active threadId/hostId и сохранённым afterCursor. Для обычной проверки достаточно timeoutMs: 0; ограниченное ожидание изменения — до 60000. Записывай новый cursor. Пока этап работает, не посылай повторный prompt, не запускай следующий и не публикуй неизменившийся статус. read_thread нужен только для отсутствующего handoff, фактической ошибки, вопроса или неоднозначного финального результата; фильтруй объём выводов.
3. Статус idle/done не равен приёмке. Проверь фактический отчёт и материалы в checkout исполнителя, результаты проверок и разумную визуальную достаточность. При новой правке достаточно проверок затронутой области; не устраивай бессрочные полные повторные циклы.
4. Если этап действительно готов, запиши report path, checkout, branch/commit ref и status accepted. Только затем запускай следующий. После create_thread или send_message сразу запиши реальный threadId/hostId и статус running, чтобы повторное пробуждение не создало дубль. При неоднозначном результате создания найди уже существующий чат через list_threads/read_thread, а не создавай второй.
5. Если результат частичный, верни конкретный остаток тому же исполнителю через send_message_to_thread: владелец разрешил такие продолжения. Не переходи дальше на основании одного уверенного финального текста.
6. Если кейс упёрся в реально отсутствующий общий модуль, останови его активную реализацию на handoff, передай конкретный common-request G, дождись исправления и обновлённого ref, затем верни этот же кейс на завершение. Это дополнительный последовательный этап, не разрешение кейсу править DS самостоятельно.
7. Обычная композиция, локализация, технические исправления, закрытие подтверждённых визуальных дефектов и проверка не требуют нового ответа владельца. Новые факты о коммерческом результате не выдумывай: используй подтверждённое качественное утверждение. Настоящий внешний блокер сообщай конкретно и не объявляй готовым; продолжай доступные независимые части в текущей области.
8. После G-final запиши accepted технического checkpoint и последовательно запусти H-art-direction в том же G; не закрывай цепочку и не отключай heartbeat. Только после положительного H-art-review запиши status complete и отчёт об исполненных этапах; отключи heartbeat через automation_update, сохранив поля и установив PAUSED. Если нужен ответ владельца по внешнему блокеру, не создавай повторяющиеся сообщения каждый запуск.

## Как запускать кейсовый чат B–F

Перед созданием обязательно прочитай нужный полный файл промпта из исходного проекта; некоторые handoff-файлы появились позже базового снимка. Укажи в новом сообщении реальный base ref и источник handoff из D:/Claude-projects/Site-portfolio/tasks/portfolio-rebuild/integration/base.md.

Поскольку владелец не выбирал environment нового чата вручную, create_thread использует сохранённый проект и environment local; model/thinking не указывать — сохраняется настроенный default пользователя. В задании поручить исполнителю создать/использовать собственный управляемый worktree от записанного точного ref до первых правок кейса. Всё изменение портфолио идёт в этом worktree. Не использовать remote default вместо принятого снимка. Имена веток — codex/.

Первое сообщение: полный подготовленный промпт + краткое уточнение ночной работы. Уточнение поручает:
- выполнить только свой кейс до законченного EN/RU preview и handoff, не ждать владельца для обычных решений;
- создавать новые задачи и запускать следующий этап не нужно: этим занимается единственный контроллер;
- прочитать общий report/base.md из исходного checkout, если их нет в ref, и следовать уже замороженному ds/story-contract.md;
- передать актуальные локальные URL, checkout, ветку, evidence/media/artifact-plan/report, desktop/mobile кадры и сцену;
- после успешных проверок подготовить локальный тематический commit только своих файлов на своей codex/ветке, чтобы G мог интегрировать точную версию. Чужие и общие файлы не включать, push/deploy не делать;
- если общий запрос блокирует завершение, дать конкретный handoff без выдуманного PASS и не обходить общий владелец;
- не редактировать STATE.json контроллера.

Создавай user-visible название по кейсу; при упоминании существующего чата используй точное название, полученное через list_threads. После успешного create_thread обязательно выдавай ::created-thread с подтверждённым threadId в сообщении пользователю; setup clientThreadId не подставляй в tools, требующие настоящий threadId.
