# Sitemap — Site-portfolio

**Источник:** `outputs/prd.md` v1.0 · `ia/screens-inventory.md`
**Статус:** Фазы 1.2 + 1.3, ждёт апрува

**Приоритеты:** `[core]` — MVP v1.0 (Must have) · `[v2]` — v1.1, первая волна (Should) · `[later]` — v2.0 и отложенное (Could / Won't have now)

**Решение по форме дерева:** секции страниц входят в дерево наравне с маршрутами, ограничения по глубине нет. Маршрутов четыре, и порядок блоков внутри страницы — это и есть предмет проектирования: скрининговый пакет обязан уложиться в 2160 px, а Development обязан стоять ниже всех продуктовых блоков. Дерево, которое этого не показывает, бесполезно.

**Обозначение маршрутов:** узлы с `→ /path` — самостоятельные URL. Остальные — секции и состояния внутри родительского маршрута.

## Сквозные состояния

Не занимают места в дереве: применяются к любому маршруту, а не живут в одном.

| Состояние | Где применяется | Приоритет |
|---|---|---|
| `DirectEntryState` — прямой вход по URL отдаёт конечное состояние немедленно, без intro | все маршруты | `[core]` |
| `ReducedMotionState` — анимации отключены через `gsap.matchMedia()`, включая page transitions | все маршруты | `[core]` |
| `NoScriptView` — ≥1500 символов осмысленного текста в DOM до JS + содержательный `<noscript>` | все маршруты | `[core]` |
| `MobileHome` — мобильная главная как самостоятельный носитель, не сжатие десктопа | `Home` | `[core]` |
| `CopyEmailFeedback` — подтверждение копирования через `aria-live` | везде, где есть `ContactBlock` | `[core]` |
| `SkipLinkFocus` — skip-link и видимый фокус первым интерактивным элементом | все маршруты | `[core]` |
| `OGPreview` — пер-страничные `title`, `description`, `og:image`, `canonical`; OG-картинка с названием кейса | все маршруты | `[core]` |

## Проверка MECE

- **Каждый экран живёт ровно в одном месте.** Единственные кандидаты на дублирование — `ContactBlock`, `Nav`, `Footer` и семь сквозных состояний: они присутствуют на всех маршрутах. Разрешено так: `ContactBlock`, `Nav` и `Footer` объявлены один раз под `Home` как глобальные блоки, состояния вынесены из дерева в отдельную таблицу. Второй раз ни один узел не встречается.
- **Разделы вместе закрывают весь продукт.** Сверено против PRD §5 по ID: покрыты все IA-01…08, SCR-01…11, WRK-01…05, CASE-01…22, DEV-01…05, MOT-01…13, TECH-01…16, MEAS-01…04. Требования, не имеющие экранного представления (TECH-09 LCP, TECH-10 woff2, MOT-12 тест на загруженной машине, MEAS-04 ручной учёт), в дерево намеренно не внесены — это нефункциональные свойства, а не узлы ИА.
- **Глубина** — до четырёх уровней там, где это несёт смысл (`Home → CaseDSSL → CaseHeader → CaseOutcomeLine`). Ограничение снято решением владельца.

## Три места, где приоритет спорный

1. **`CaseRework` помечен `[core]`, хотя решение владельца №2 не принято.** Основание: PRD называет вариант (а) — «реальная реализация как основа, переработка отдельным помеченным блоком» — предпочтительным, а CASE-18 стоит в Must. Если владелец выберет вариант (в) «оставить как есть», узел исчезает целиком, и это единственная правка схемы кейса.
2. **`AboutExperience` помечен `[v2]`, хотя стоит одну строку.** Основание: SCR-05 лежит в Should, а решение владельца №3 не принято. Если решение будет «указывать» — переводится в `[core]` без последствий для структуры.
3. **`LocaleRU` помечен `[core]`, хотя русских текстов в v1 не будет.** Каркас маршрутов и `hreflang` требуются TECH-13 с первого дня — задним числом это чинится дорого. В MVP входит скелет, не контент.
