# Agent Ops — Final Design Refinement · план этапа

28.11.2026 · PF-3 · **план, не запуск.** Этап 7A в [PLAN-CHATS](../../PLAN-CHATS.md). Исполнитель — Claude. Реализация начинается только после implementation brief ChatGPT и отдельного слова владельца.

## 1. Зачем этап

Agent Ops визуально не считается готовым (владелец, 27.11.2026). Направление Shift Board утверждено 25.11.2026, Q1 по трём экранам пройден, но выбранные экраны ещё не доведены до уровня, на котором каждый кадр кейса работает сам по себе. Этап доводит три экрана, а не меняет продукт.

**Цель.** Довести Review Queue, Run Detail и Action Approvals до максимального профессионального уровня внутри утверждённой светлой арт-дирекции. Сохранить идентичность Agent Ops, бизнес-логику и достоверность интерфейса. Получить сопоставимые BEFORE/AFTER и независимую приёмку.

**Чем кейс Agent Ops отличается от двух других.** Это история взаимодействия с AI-системой: проверка того, что агент обещал, принятие решений, доверие и управление риском. Экраны доводятся под эту историю.

## 2. Границы

| Делаем | Не делаем |

**Секции для R2** (рабочий перечень, уточняется по брифу и BEFORE):
- **Review Queue:** шапка смены и операционный сигнал; переключатель областей (NAV-01); строка записи в очереди и кластеры; просрочка и SLA (SLA-01); фильтры и сортировка; пустая и здоровая очередь; переход к прогону.
- **Run Detail:** шапка с обещанием агента и вердиктом; находка; связанные доказательства (Conversation / Trace, RUN-01 на телефоне); веса пропуска; действия оператора и Undo; Prev / Next и FLOW-01; крупные числа и метаданные (TYPO-01).
- **Action Approvals:** поперечная очередь с ходом смены и SLA; выбранная запись: сумма и основание; два последствия (изменение по счёту, сообщение клиенту); подтвердить / отклонить с причиной; объяснение эскалации; ограничение порога политики (решение 1 Stage 2.8.5).

## 5. Здоровый сценарий первым

Портфолио не должно показывать продукт, который состоит из ошибок и блокировок. Здоровое состояние показывается внутри трёх экранов, существующей функциональностью:

| Экран | Первое показанное состояние | Сложный случай — вторым |
|---|---|---|
| Review Queue | Смена идёт по плану, большая часть прогонов проверена, в очереди немного записей | Кластер с находкой |
| Run Detail | Прогон, где обещания агента подтверждены связанными доказательствами | Пустой трейс с четырьмя разными находками |
| Action Approvals | Выплата в пределах политики, подтверждённая оператором с видимыми последствиями | Перехват выплаты и отклонение с причиной |

Если нужного здорового состояния в фикстуре нет, его добавляют синтетическими данными в той же модели, без новой функции. Autonomy не возвращается в scope ради здорового состояния.

## 6. Что не меняется

- Направление Shift Board, светлая тема, типографика и цветовая логика из `DIRECTION-SPEC.md`. Сильные принятые решения: поперечная очередь Approvals, связка суммы и основания с двумя последствиями, единая плоскость обещания и доказательства в Run Detail.
- Бизнес-правила продукта — матрица RULE-01 сверяется до приёмки каждого экрана.
- Достоверность: синтетические данные, роли моделируются локально (AUTH-01, DATA-01), это не выдаётся за интеграцию.
- Ограничение Approvals: без первичных данных порог политики не придумывается. Q2 Approvals остаётся PARTIAL, пока владелец не передаст первичные записи.

## 7. Конфиденциальность

Ограничения NDA не зависят от визуальной готовности. В переработке нет ничего из переданного клиенту: интерфейса, кадров, данных, текстов. Кадры и доказательства этапа — только в приватном репозитории и `D:\Design\Cases\Case\`. В Site-portfolio — только статус этапа. Публикация любого артефакта — по разрешению владельца ([DIRECTION 7.1](../../DIRECTION-2026-11.md)) и после закрытия P0.

## 8. Критерии завершения

1. Каждая секция трёх экранов разобрана в R2. Каждая правка имеет причину и доказательство. Секции без правок отмечены как сохранённые с причиной.
2. Q1 PASS по трём экранам во всех показанных кейсом состояниях. Q2 Review Queue и Run Detail — PASS; Approvals — не ниже принятого PARTIAL.
3. Responsive QA без критических переполнений и недоступных действий на 360–1440. Axe без нарушений. Клавиатурный путь каждого сценария работает.
4. Стоп-лист пройден на каждом изменённом экране. Тест подмены и Cross-product с Partner Portal и Learn — PASS. Отличия Agent Ops не сглажены.
5. Первое показанное состояние каждого экрана — здоровое.
6. Сопоставимые BEFORE/AFTER по каждому экрану.
7. Бизнес-правила RULE-01 сверены. Нет новых функций, которых нет в продукте.
8. Независимая приёмка ChatGPT (G5) и решение владельца. Claude свою работу не утверждает.

## 9. Параллельность

- Этап идёт параллельно с Partner Portal у Codex: другой репозиторий (`Agent-ops-console`), своя ветка `claude/agent-ops-final-refinement`. Общих файлов с Codex нет.
- Для Cross-product нужны кадры Partner Portal и Learn — берутся по закреплённым SHA, только чтением.
- Этап не ждёт этапа 6. Внешнее ревью пилотного кейса нужно до кейса Agent Ops (этап 7B), а не до доводки продукта.
- Этап не блокирует Partner Portal и Learn. Если он не успевает к релизу, портфолио выходит без Agent Ops.

## 10. Решения владельца в этом этапе

Только три, и только когда до них дойдёт работа:
1. Слово на старт этапа после брифа ChatGPT.
2. «Ок» после первого доведённого экрана.
3. FLOW-01 (автопереход в Run Detail после Undo) — только если бриф предлагает его менять.

Ограничение Approvals (решение 1 Stage 2.8.5) владелец принимает отдельно, в общем списке [REMAINING-WORK §A](REMAINING-WORK.md#a-решения-владельца).
