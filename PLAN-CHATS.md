## Общие правила для всех чатов

- Первым делом прочитать [DIRECTION-2026-11.md](DIRECTION-2026-11.md) целиком. Решения оттуда не пересматривать без прямого слова владельца.
- Стоп-лист AI-умолчаний (раздел 5 DIRECTION) проверяется на **каждом** экране, который чат создаёт или меняет. Нарушение — не закрытие этапа.
- Claude предлагает варианты и рекомендацию, выбор — за владельцем. Утверждать направления и экраны самому нельзя.
- Рисуем в коде, Figma не используется.
- Репозиторий Site-portfolio публичный. Материалы DSSL без скрытия, реквизиты, цены, имена сотрудников — только в `D:\Design\Cases\Case\`, в репозиторий не кладутся.
- Маскирование и переработка не дают права на публикацию (DIRECTION, 7.1). Любой чувствительный артефакт — в том числе кадры из `Прод-2026-11/скрыто-NDA/` и переработанные версии Agent Ops и Learn — попадает на сайт или в репозиторий только при записи о разрешении владельца в `evidence-inventory`.
- Факты не выдумываем. Нет метрик — пишем, что есть (внедрение, приёмка, тесты), и где граница выводов. Даты сверять с памятью `owner-work-chronology` и разделом 8 DIRECTION.
- Тексты публичных страниц — по [CONTENT-RULES.md](CONTENT-RULES.md): без меток «концепт».
- Дизайн-система сайта — по `ds/CONTRACT.md`; зеркала `ds/` → `src/` обновляются тем же коммитом. ДС продуктов живут в их репозиториях.
- Закрывая этап: обновить статус в карте выше, записать выходы, коммит в ветке этапа (см. «Git и выкладка»).

## Git и выкладка — инварианты для всех этапов

Main сайта kanarev.com выкладывается в production **автоматически**. Для репозиториев прототипов (b2b-dssl, Agent-ops-console, learn) считать так же, пока не доказано обратное.

1. **Изоляция.** Каждый этап работает в своей ветке `stage-<N>-<slug>` (или отдельном worktree) в каждом затронутом репозитории. Рабочий каталог владельца с его незакоммиченными изменениями не используется.
2. **Base SHA.** В начале этапа записать base SHA каждого затронутого репозитория в отчёт этапа (`tasks/review-2026-11/stage-<N>.md`). База — main после согласованного merge предыдущего этапа; если владелец предыдущий этап ещё не мержил — голова его ветки (записать, какой вариант взят). Если main ушёл вперёд — не перебазироваться молча, сказать владельцу.
3. **Чужие изменения.** Не откатывать, не перезаписывать и не коммитить чужие правки; в коммит — только свои файлы по имени, без `git add -A` / `.`.
4. **Без согласования владельца нельзя:**
   - merge в main и push в main;
   - production-деплой (включая любое действие, которое его запускает);
   - изменение внешних профилей и публичных документов: Upwork, hh, LinkedIn, опубликованное резюме.
   Согласование — отдельное явное слово владельца на конкретное действие («мержим stage-3», «публикуем»), а не общий «ок» этапа.
5. **Push ветки** допустим только с согласия владельца: он может запустить preview-деплой в публичном окружении. Перед push — проверка содержимого на чувствительные данные (DIRECTION, 7.1).
6. **Preview, не production.** Проверка «в браузере» на этапах 1–8 — локальная сборка или preview ветки.
